On 2026-10-06 the current upstream setup script was downloaded and executed as root in a dedicated Ubuntu VM overlay. Windows host services and network settings were not changed. The installer downloaded `/usr/local/bin/DaggerLauncher`; its SHA-256 is `cb3652fee0776896ceac4569b497449b510c0c4ee0d5a9bdf5f1ee82e7962ed9`, identical to the originally supplied launcher.

The launcher's live `--list-versions --role server` response confirmed `release.latest = v4.2.8`. The setup script SHA-256 was `139a56db18d8c5611c9d6dba93edfdc95fbce76881f97f20abbdbdf47913e4f1`.

Core retrieval was attempted with `DC_CHANNEL=release` and `DC_VERSION=v4.2.8`, an isolated test configuration and a freshly generated test PSK. A traced run failed its license request. A second, untraced run using the VM's actual public egress address also exited with:

```text
launcher: license fetch failed: license check failed: license denied: license_denied
```

The second run rules out the private VM address and ptrace tracing as sufficient explanations for this result. It does not establish what license entitlement or configuration would be accepted. No v4.2.8 core was delivered by that installer attempt. The live version listing is public; access to the core was not granted to the test configuration.

Ghidra MCP decompilation of the unchanged launcher at `0x69d0c0` confirms that its execution path takes separately delivered executable bytes, writes a Linux memory file and executes it. A successful installation can therefore expose the running executable through `/proc/PID/exe`, even when no persistent `DaggerConnect` binary appears beside the launcher. This is not a claim that the unsuccessful test reached that path.

## Export from an existing installation

On a server you administer with a successfully running DaggerConnect core:

```sh
sudo bash scripts/export-running-core.sh YOUR_SERVICE_NAME ./core-export
```

The helper copies only the selected executable, refuses the launcher and unrelated executables, preserves existing output, and prints its SHA-256. It does not read configurations, environment variables, process memory, or the launcher's separate claims/key descriptors. It makes no network requests and cannot obtain a core from a rejected license request. The exported candidate's version still needs verification.

Upstream: [setup script](https://github.com/itsFLoKi/DaggerConnect/blob/main/setup.sh), [XHTTP documentation](https://github.com/itsFLoKi/DaggerConnect/blob/main/xhttp.md).
